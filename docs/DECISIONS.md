# Принятые решения

Одна строка на решение: что выбрано там, где ТЗ допускало варианты.

## Структура и инфраструктура

- Файлы моделей и схем названы во множественном числе (`users.py`, `vacancies.py`), как в исходных набросках.
- `docker-compose.yml` лежит в `back/`, потому что git-репозиторий находится там; при добавлении frontend его можно перенести на уровень выше.
- Порты контейнеров на хосте настраиваются через `DB_HOST_PORT` и `BACKEND_HOST_PORT` в `.env` (на машине разработчика 5432 занят локальным PostgreSQL, поэтому `db` проброшен на 5433).
- Внутри compose backend всегда ходит на `db:5432`: `POSTGRES_HOST` и `POSTGRES_PORT` переопределены в `docker-compose.yml`.
- Seed запускается как модуль: `python -m scripts.seed`; при непустой таблице `users` ничего не делает.
- Тестовая схема создаётся в фикстуре через `Base.metadata.create_all` (только в тестах, в приложении `create_all` нет); таблицы очищаются `TRUNCATE` перед каждым тестом.
- Ruff: правило UP042 отключено, потому что ТЗ требует enum'ы вида `(str, enum.Enum)`.

## API

- `GET /health` находится под общим префиксом: `/api/v1/health`; при недоступной БД отвечает 503.
- Несуществующая категория в теле вакансии даёт 422 с кодом `category_not_found` и полем `body.category_id`, чтобы форма подсветила select.
- `GET /vacancies/my` и `GET /admin/vacancies` возвращают тот же формат страницы `{items, total, limit, offset}`, что и публичная лента; `status` в них необязателен.
- `GET /vacancies/{id}` открывает опубликованную вакансию даже после дедлайна (в ленте её уже нет).
- Если на публичный эндпоинт пришёл невалидный токен, ответ 401, а не «аноним».
- Отклик на вакансию не в статусе `published` даёт 404 (студент её не видит), на просроченную — 409 `vacancy_expired`.
- Статус отклика: повторная установка `viewed` разрешена (интерфейс может помечать просмотр при каждом открытии), `accepted` и `rejected` конечные.
- Резюме доступно только студенту-автору и владельцу вакансии; остальным, включая администратора, 404.
- Категории требуют явный `slug` (латиница): автогенерация из кириллицы потребовала бы транслитерации.
- При одобрении вакансии старый `moderation_comment` очищается.
- Повторная отправка на модерацию запрещена, если дедлайн уже прошёл (409 `vacancy_deadline_passed`).

## Валидация и данные

- «Сегодня» для дедлайнов считается по UTC (`today_utc`), как и время в БД.
- Вакансия считается непросроченной в день дедлайна включительно (`deadline >= сегодня`).
- Фильтр `course` показывает вакансии с таким `target_course` и вакансии без него («для всех курсов»).
- Фильтр `salary_from` и сортировка `salary` используют верхнюю границу: `coalesce(salary_max, salary_min)`; вакансии без зарплаты идут последними.
- Сортировка `salary` и фильтр `salary_from` сравнивают числа без пересчёта валют (UZS и USD не конвертируются).
- Поиск `q` — регистронезависимый `ILIKE` по `title` и `description`.
- Стандартные сообщения Pydantic переводятся на русский по типу ошибки в `app/core/exceptions.py`, а не дублируются валидаторами в каждой схеме.
- Ошибки `model_validator` привязываются к конкретному полю через `FieldError`, чтобы в ответе было `body.course`, а не просто `body`.
- В БД добавлены CHECK сверх ТЗ: `email = lower(email)`, `course BETWEEN 1 AND 6`, неотрицательная зарплата, формат `student_id`.
- После изменения вакансии сервис перечитывает её одним запросом с `selectinload`, а не использует `refresh` (из-за `lazy="raise"`).
- Сервис откликов принимает `UploadFile` как файловый объект; HTTP-ошибок он при этом не создаёт, только `AppError`.

## Вход по ID студента

- Добавлено необязательное поле `users.student_id` (ровно 7 цифр, уникальное, только для студентов).
- В `POST /auth/login` поле `username` принимает email или ID студента: строка из 7 цифр ищется по `student_id`.
- Отдельного поля для паспорта нет: номер паспорта можно задать как пароль при регистрации (формат «2 буквы + 7 цифр» проходит правило пароля), в БД он хранится только как Argon2-хеш, в открытом виде нигде не сохраняется и не логируется.
- Проверить, что ID и паспорт принадлежат реальному студенту, без доступа к базе университета нельзя: это вынесено в следующие шаги (интеграция с БД/SSO университета).
- Ограничение: номер паспорта как пароль слабее обычного пароля (его знают третьи лица, формат предсказуем), поэтому для продакшена нужны rate limiting на вход и принудительная смена пароля после первого входа.

# Следующие шаги

1. **Интеграция с БД и SSO университета.** Проверять `student_id` и паспорт по базе университета или заменить локальный вход на SSO (OAuth2/OIDC); подтягивать ФИО и курс автоматически.
2. **Telegram-бот для автопубликации.** После `approve` отправлять вакансию в канал отдельной фоновой задачей через `httpx.AsyncClient`; токен в настройках; ошибка бота не должна ломать публикацию.
3. **Email-уведомления.** Работодателю о решении модератора и новом отклике, студенту о смене статуса отклика.
4. **Rate limiting.** Ограничить попытки входа и регистрации по IP и логину (особенно важно при входе по ID студента).
5. **S3 для файлов.** Перенести резюме из локального volume в S3-совместимое хранилище, отдавать по временным ссылкам.
6. **Refresh-токены и выход.** Сейчас только короткоживущий access-токен.
7. **Полнотекстовый поиск.** Заменить `ILIKE` на `tsvector` + GIN-индекс при росте числа вакансий.
8. **Frontend в compose.** Добавить сервис `frontend` (Vue 3) и общий reverse proxy.
